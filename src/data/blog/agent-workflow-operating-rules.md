오늘 작업을 시작하면서 제일 먼저 한 일은 `main`으로 돌아가서 `git pull --rebase`를 하는 것이었다.

별것 아닌 습관처럼 보이지만, AI 코딩 에이전트를 쓸 때는 이런 작은 운영 규칙이 생각보다 중요하다. 에이전트가 코드를 잘 쓰는지는 모델 성능의 문제지만, 에이전트가 안전하게 일하는지는 작업환경의 문제이기 때문이다.

나는 요즘 AI 코딩 에이전트를 "똑똑한 자동완성"보다 "권한을 가진 junior operator"에 가깝게 보고 있다.

자동완성은 틀리면 지우면 된다. 하지만 operator는 브랜치를 바꾸고, 파일을 수정하고, 명령을 실행하고, 외부 서비스에 접근한다. 그래서 필요한 질문도 달라진다.

**이 에이전트가 무엇을 할 수 있는가?**

보다 먼저,

**이 에이전트가 어떤 경계 안에서 일하고 있는가?**

를 봐야 한다.

---

## 실패는 모델 안에서만 오지 않는다

최근 흥미로운 논문을 읽었다. Claude Code, Codex, Gemini CLI의 공개 이슈 3.8K건 이상을 분석한 연구다.

결론 중 인상적인 부분은 이렇다. 버그의 67% 이상이 기능 관련 문제였고, root cause로는 API, integration, configuration 문제가 36.9%를 차지했다. 증상으로는 API error, terminal problem, command failure가 많이 나왔다. 문제가 주로 발생한 위치도 tool invocation과 command execution 단계였다.

즉, 실패는 단순히 "모델이 코드를 잘못 짰다"에서만 오지 않는다.

오히려 실무에서 자주 아픈 지점은 이런 곳이다.

- 명령이 어느 디렉토리에서 실행됐는지
- 어떤 파일까지 읽고 쓸 수 있는지
- 인증 토큰이 살아 있는지
- sandbox가 네트워크나 파일 쓰기를 막았는지
- package manager가 lockfile과 맞는지
- test 실패 로그가 다음 수정에 제대로 들어갔는지
- unrelated change를 같이 stage하지 않았는지

이건 모델 벤치마크보다 훨씬 지루한 문제다. 그런데 바로 이 지루한 부분이 에이전트의 실사용 품질을 결정한다.

## 프롬프트보다 먼저 작업 프로토콜

AI 에이전트를 잘 쓰고 싶을 때 보통 프롬프트부터 고치고 싶어진다.

"더 정확히 지시해야 하나?"

"role을 더 자세히 줘야 하나?"

"출력 형식을 강제해야 하나?"

물론 필요하다. 하지만 코딩 에이전트에서는 프롬프트보다 먼저 정해야 할 운영 규칙이 있다.

예를 들면 이런 것들이다.

1. **항상 최신 base에서 시작한다**

   작업 전에 `main`으로 돌아가고, `git pull --rebase`를 한다. 에이전트가 낡은 컨텍스트 위에서 열심히 일하는 순간, 뒤에서 conflict 비용이 자란다.

2. **작업 단위를 브랜치로 격리한다**

   블로그 글이면 `post/*`, 기능이면 `feature/*`, 수정이면 `fix/*`처럼 브랜치 이름에 의도를 남긴다. 브랜치는 에이전트에게 주는 작업 울타리다.

3. **불필요한 파일은 stage하지 않는다**

   특히 개인 프로젝트에서는 untracked file이 자주 섞인다. `git add -A`는 편하지만, 에이전트에게는 너무 큰 빗자루일 때가 많다.

4. **검증 명령을 작업의 일부로 둔다**

   글이면 build, 코드면 test와 lint가 필요하다. 검증은 마지막 의식이 아니라 에이전트 루프의 센서다.

5. **실패 로그를 숨기지 않는다**

   에이전트가 실패했을 때 중요한 건 "다시 해줘"가 아니다. 어떤 명령이, 어떤 권한에서, 어떤 로그로 실패했는지를 다음 입력으로 넣어야 한다.

이 정도만 지켜도 에이전트의 체감 품질은 꽤 달라진다.

## 에이전트에게 필요한 것은 작업 기억이다

사람 개발자도 매번 처음부터 일하지 않는다.

이 프로젝트는 어떤 브랜치 전략을 쓰는지, publish 전에는 무엇을 확인해야 하는지, 어떤 파일은 건드리면 안 되는지, draft와 publish의 기준은 무엇인지 같은 기억이 있다.

AI 에이전트도 마찬가지다. 매번 채팅창에서 설명하면 곧 흐려진다. 그래서 프로젝트 안에 운영 규칙이 있어야 한다.

예를 들어 이 블로그에서는 이런 규칙들이 중요하다.

- 글은 `src/data/blog/`에 둔다.
- 한국어를 기본으로 쓴다.
- draft 단계에서는 `draft: true`를 유지한다.
- publish 요청이 있을 때만 `draft: false`로 바꾼다.
- PR에는 관련 파일만 포함한다.
- `pnpm-workspace.yaml` 같은 unrelated untracked file은 건드리지 않는다.
- push 전에는 `npm run build`를 확인한다.

이 규칙은 모델의 지능을 높이지 않는다. 대신 모델이 실수할 공간을 줄인다.

좋은 agent workflow는 모델에게 더 많은 자유를 주는 방식이 아니라, 자유가 의미 있게 작동하는 환경을 만드는 방식에 가깝다.

## 권한은 생산성 기능이다

에이전트 보안 이야기를 하면 보통 거창하게 들린다.

하지만 개인 작업에서도 권한은 생산성 문제다.

에이전트가 모든 파일을 마음대로 바꿀 수 있으면 빠를 것 같지만, 실제로는 사람이 계속 감시해야 한다. 반대로 읽기, 쓰기, 실행, 네트워크 접근의 경계가 명확하면 사람은 더 안심하고 큰 작업을 맡길 수 있다.

권한이 명확해야 위임이 커진다.

이 점에서 sandbox, approval, branch, diff review는 단순한 안전장치가 아니다. AI 에이전트와 오래 일하기 위한 인터페이스다. 사람은 모든 token을 감시할 수 없지만, 경계와 로그와 diff는 검토할 수 있다.

나는 앞으로 코딩 에이전트의 차이가 모델 성능만이 아니라 이 운영 인터페이스에서 많이 갈릴 것 같다.

## 좋은 에이전트 루프의 모양

내가 지금 개인 프로젝트에서 선호하는 루프는 이렇다.

1. `main` 최신화
2. 작업 브랜치 생성
3. 관련 파일만 읽기
4. 작은 변경
5. build/test/lint 실행
6. diff 확인
7. 관련 파일만 stage
8. commit
9. PR 생성
10. 리뷰에서 나온 피드백을 다시 같은 루프로 처리

재미있는 점은, 이 루프가 사람에게도 좋다는 것이다.

AI 에이전트를 위해 작업환경을 정리하다 보면 프로젝트 자체가 좋아진다. 빌드 명령이 명확해지고, 브랜치 전략이 생기고, 문서가 정리되고, 반복되는 실수가 줄어든다.

에이전트는 여기서 일종의 압력 테스트가 된다. 사람이 암묵적으로 알고 있던 절차를 명시하지 않으면 에이전트가 흔들린다. 그 흔들림을 고치다 보면 프로젝트의 운영 지식이 문서와 스크립트로 남는다.

---

## 결론

AI 코딩 에이전트는 코드보다 작업환경에서 더 자주 실패한다.

적어도 내가 체감하는 문제는 그렇다. 모델이 함수를 못 짜서 막히는 일보다, 어떤 파일을 건드려야 하는지, 어떤 명령을 실행해야 하는지, 어디까지 권한을 줘야 하는지, 실패 로그를 어떻게 다시 루프에 넣을지에서 품질 차이가 난다.

그래서 앞으로 중요한 능력은 프롬프트를 잘 쓰는 것만이 아닐 것이다.

AI 에이전트가 들어와도 무너지지 않는 작업환경을 만드는 능력. 브랜치, 권한, 테스트, 로그, PR, 문서가 하나의 루프로 돌아가게 만드는 능력.

나는 이게 AI agent 시대의 꽤 실용적인 engineering skill이라고 생각한다.
